# 装备负载执行器（loadout-executor）

React + Vite + Zustand 的装备负载演示系统：槽位兼容、互斥标签、条件效果、套装分档、失效引用定位、
原子发布，以及**增量规则求值**（依赖查找 / 阈值更新 / 效果发布三段拆分）与全量参照的逐规则对照。

## 启动界面

```bash
npm install
npm run dev
```

开发服务器固定监听 **http://127.0.0.1:5199**（`vite.config.ts` 中 `strictPort: true`，端口被占用会直接报错而不是漂移）。

打开后页面由这些面板组成（从上到下）：

| 面板 | 作用 |
|---|---|
| 角色 / 诊断 | 基础属性、存活状态；草稿的阻断/警告列表 |
| 装配 | 每个槽位的下拉换装；封禁槽位；套装件数与档位徽章 |
| 派生状态与来源审计 | 当前方案实际生效的来源（实例 uid / 套装档位）、技能、未激活原因 |
| 发布链路 | **发布修订** 按钮；来源级激活/撤销报告；发布历史 |
| 战斗假人 | **执行攻击** 按钮；同随机种子下按修订存档的伤害与生效技能 |
| 增量求值审计 | 最近一次**真实发布**的三阶段耗时、重算/复用规则数、增量与全量等价结论 |

### 战斗演练（界面操作路径）

1. 初始方案直接点“执行攻击”，记录基线伤害（种子目录下为 54）。
2. 头盔选 `u-dhelm`、胸甲选 `u-dchest` → 徽章显示“2件 / 第2档” → 点“发布修订”。
3. 再点“执行攻击”，套装来源激活、伤害变化（84）。
4. 护手选 `u-dgloves`、战靴选 `u-dboots` → “4件 / 第4档” → 发布 → 攻击（288）。
5. 卸掉护手与战靴 → 发布 → 攻击回落（84），并在变化报告中出现“套装 set_dragon 档位 4 → 2”与来源撤销。

所有数值都来自真实 store 的发布与战斗执行，面板不写死套装效果或伤害。

## 增量求值的实现

- `src/domain/evaluate.ts`：全量参照，每次都从 `(baseStats + 当前负载)` 完整重算，无跨次残留。
- `src/domain/effectIndex.ts`：静态索引（规则 → 依赖标签 / 套装 / 属性键）。
- `src/domain/incremental.ts`：增量求值器，把全量重建拆为三段
  1. **依赖查找**：槽位 diff + 标签翻转 / 基础属性变化的反向索引失效标记；
  2. **阈值更新**：只对部件数变化的套装重算档位；
  3. **效果发布**：以“槽位 / 套装”为整块缓存，脏块重算、干净块引用拼接。
- `src/domain/publish.ts`：先校验、后单次替换的原子发布；`buildChangeReport` 产出来源级激活/撤销。
- `src/domain/equivalence.ts`：逐 trace 对照来源身份（`item:uid:itemId:ruleId` / `set:setId:threshold:ruleId`）、
  激活状态、未激活原因、属性、技能、套装档位/件数，以及来源级撤销事件——**不以总属性相同判定等价**。
- 目录版本切换走 `rebase()`，清空索引、依赖表与全部缓存后按新目录重建，旧效果不会残留。


> 本沙箱的 Chromium 依赖不在系统路径中。Playwright 配置已把
> `/tmp/pwlibs/usr/lib/aarch64-linux-gnu:/tmp/pwlibs/lib/aarch64-linux-gnu` 注入

## 性能测量

```bash
npm run bench        # 完整测量（每格 64 步 × 4 轮，约一分钟）
npm run bench:quick  # 快速测量（每格 16 步 × 2 轮）
```

- 结果写入 `bench/results/latest.md` / `latest.json`。
- 耗时用独立循环计两条路径，并重复多轮取平均，避免交替调用造成的多态时钟偏差与容器调度噪声；
  分配量由独立子进程配合 `--expose-gc --trace-gc-nvp` 分段统计；
  索引建立成本由 `bench/index-probe.ts` 在独立进程内预热后测量，不与求值循环混在一起。
- 输出包括：**索引建立成本**、每步全量/增量耗时与三段拆分、分配量、逐规则等价 / 撤销 / 变化报告一致性。

### 实测结论（多次运行的观测范围）

`bench/results/latest.md` 是最近一次完整运行的原始数据；下面是多次运行后稳定的结论区间
（容器环境有调度噪声，单次数值会有 ±30% 波动，因此按区间表述）。

| 规模 | 单槽位 | 整套 | 整备 |
|---|---|---|---|
| small（6 槽 / 28 规则） | 0.6–1.1x | 0.3–0.9x | 0.2–0.3x |
| n16（16 槽 / 284 规则） | 1.0–1.2x | 0.24–0.37x | 0.25–0.32x |
| n32（32 槽 / 1209 规则） | 1.4–1.7x | 0.77–0.87x | 0.51–0.55x |
| n64（64 槽 / 4222 规则） | 1.7–1.9x | 1.30–1.32x | 0.43–0.45x |

分配量（全量 / 增量，每步）：

| 规模 | 单槽位 | 整套 | 整备 |
|---|---|---|---|
| small | 0.79x | 0.79x | 0.57x |
| n16 | 1.45x | 0.75x | 0.69x |
| n32 | 约 2.0x | 1.23x | 0.77x |
| n64 | 2.16x | 1.52x | 0.73x |

索引建立成本（独立进程、预热后 15 次构造取中位数）：
small 约 0.06–0.08 ms / 约 104 KiB；n16 约 0.22 ms / 约 358 KiB；
n32 约 0.64–0.67 ms / 约 1.20 MiB；n64 约 1.6–1.9 ms / 约 3.83 MiB。
所有行等价、撤销事件、变化报告均一致（差异 0）。

**退化说明（如实保留）：**

- 小规模输入（small / n16）的增量调度开销无法摊薄，整套与整备行明显慢于全量；
  small 单槽位接近全量，n16 单槽位开始反超。
- 整备换装（all-slots）会触及几乎所有槽位块，增量路径的逐规则缓存与块拼接开销超过全量单趟循环，
  因此所有规模的整备行都慢于全量。
- 增量优势出现在大目录的**局部修改**：n16/n32/n64 单槽位，n64 整套已开始超过全量；
  这些行的分配量同样显著低于全量（n64 单槽位约 2.2x 更少分配）。
- 索引建立是一次性成本，n64 约 1.6–1.9 ms / 3.83 MiB，需要足够多次局部修改才能摊平；
  small 的索引建立与单步耗时同量级。

增量路径没有减少校验项（发布前的阻断错误检查完全保留），也没有把发布推迟到未计时阶段：
三段耗时都在 `metrics` 中单独记录，面板展示的正是真实发布时的值。
